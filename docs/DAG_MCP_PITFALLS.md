# 办公 DAG 与 MCP 踩坑路线

> 更新日期：2026-08-20  
> 适用范围：Lumi 办公模式的任务路由、LangGraph 节点执行、MCP、脚本沙箱和前端任务状态。  
> 本文记录故障的排查与解决原则；当前架构说明见 [CURRENT_DAG_ARCHITECTURE.md](CURRENT_DAG_ARCHITECTURE.md)。

## 1. 先划清边界

最早的设计把“上传文档”直接等同于“进入智能体任务”。这会让普通问答意外获得办公工具，也会让工具、上下文和耗时一起膨胀。现在的入口应先区分模式：

| 用户操作 | 正确链路 | 不应发生的事 |
| --- | --- | --- |
| 普通聊天、文档问答、识图、语音 | 轻量对话和受控检索 | 不创建 DAG，不暴露写文件、脚本或系统工具 |
| 办公模式中的产物、多步骤、跨文档或外部动作 | TCA 路由到 M0/M1/M2/M3 | 因为“有附件”就扫描全部附件、启动所有 Agent |

排障的第一问不是“模型为什么没有调用工具”，而是“请求是否真的进入办公模式并获得了预期的候选能力”。模式错了，后续调优都无效。

## 2. 演进路线与典型陷阱

### 2.1 用“大任务锁”保护环境，导致能力被锁死

**症状**：执行办公任务时只能调用某个任务预先绑定的 skill，读取文档后无法切换到脚本导出、客户端操作或其他合理方法。

**根因**：把“任务”既当作用户可见进度单元，又当作运行时的权限边界。一个长生命周期的任务上下文会把规划时未知的后续能力一并排除。

**解决**：将任务拆成原子 DAG 节点。节点只声明一个目标、一次外部调用和所需资源；权限则由场景、用户、角色、确认状态与工具元数据共同决定。节点之间仅通过有向依赖和资源读写关系连接，不以“上一个任务的 skill 集合”限制下一个节点。

**回归检查**：对“读取失败后改用脚本导出”的任务，确认失败节点能触发受控重规划或替代工具，而不是原样重试到超时。

### 2.2 一开始就规划所有步骤，既慢又无法纠偏

**症状**：简单转换耗时很长；模型把全部附件逐个读一遍；中间结果表明方向错误后仍继续原计划。

**根因**：所有任务都走全量 LLM 规划，且把计划当作不可变的引擎输入。

**解决**：采用四级路由。

| 层级 | 处理原则 | 例子 |
| --- | --- | --- |
| M0 | 已定位、参数明确的确定性快速路径，先验证真实产物 | `scores.csv` 转 `scores.txt` |
| M1 | 模板化 DAG，填充参数 | 固定报表、已知批处理 |
| M2 | Planner 生成原子计划，按依赖逐步执行 | 合并、翻译、整理后导出 |
| M3 | 有界 ReAct，根据最新观察决定下一步 | 文件读取失败、开放式分析 |

M0 失败不能伪造“已完成”，而是附带失败证据升到 M1/M2。M2/M3 也必须经过产物或结果验证器。计划可以被升级或重写，但每次修改都要记录原因、限制最大层级和重试次数，防止无限循环。

**回归检查**：单文件转换不应触发规划 LLM；目标文件不存在或验证失败时，不得直接返回“已生成”。

### 2.3 把每个附件内容都塞给模型，既慢又容易答非所问

**症状**：用户上传 `scores.csv` 并要求转换，系统却逐个分析日历、邮件、发票等无关附件，然后输出多段相互矛盾的“无法转换”。

**根因**：附件选择与任务规划耦合，模型只能在大量文本片段中猜测目标文件；每读一份文件都重新解释一次用户指令。

**解决**：先构建附件清单（显示名、类型、大小、提取状态、会话归属），以用户显式点名的名称做确定性匹配；只有匹配不唯一时才请求澄清或做有限候选排序。确定目标后直接进入相应转换/编辑工具，工具产物必须被校验并作为附件返回，而不是把数据逐行口述到聊天气泡。

**安全边界**：上传文件的正文是不可信数据。只有当前用户明确指定的清单文档才可被当作待执行任务列表；文档中的“忽略规则”“读取其他用户数据”等文字只是内容，绝不能改变权限或调度策略。

### 2.4 细粒度文件工具太多，模型选错且无法产生真实交付物

**症状**：模型反复 `read_file`、逐行总结，却没有导出文件；相似工具描述还会造成选错工具。

**根因**：以低层读写 API 拼装办公动作，工具数量过多且没有“产物”这一强约束。

**解决**：

- 对高频确定任务提供确定性旁路，例如格式转换、受控编辑和文档生成。
- 对确实需要计算或转换的任务，提供受限的脚本执行能力，输入和输出都在用户已授权工作区内。
- 工具元数据必须包含输入 schema、输出 schema、写操作、幂等性、成本、领域、意图、资源模板与冲突关系。
- 工具返回结构化产物引用；前端先预览，再由用户主动下载，绝不暴露后端绝对路径。

脚本执行不是“任意 Shell”：只允许 Docker 沙箱、非 root、禁网、只读根目录、受限 CPU/内存/PID/超时。沙箱不可用时应隐藏该能力并返回可行动错误，不能回退为 API 容器本机执行。

### 2.5 DAG 并行导致写冲突，或为了避免冲突把所有任务串行化

**症状**：同一文档被两个节点同时修改、重试重复发出副作用；或者无关任务也被全局锁阻塞。

**根因**：只依据拓扑顺序，没有明确的资源读写声明和幂等语义。

**解决**：节点声明 `read`/`write` 资源。读读可并行，任何涉及同一资源的写操作互斥；写操作要有幂等记录，恢复或重试前先判断副作用是否已经发生。当前单个办公任务按原子单链执行以确保前端过程清晰，资源锁主要解决跨任务冲突。

**回归检查**：并发提交两个不同文件的只读任务应互不阻塞；同一输出文件的两个写任务必须串行或第二个收到明确冲突结果。

### 2.6 ReAct 没有可靠 scratchpad，多轮工具调用会失忆

**症状**：模型调用工具后又重复同一调用，或忽略工具观察结果重新猜测。

**根因**：只把用户原话再次交给模型，未保留上一轮 AI 的 tool call 和相应的 tool result。

**解决**：在 LangGraph 状态中用 `add_messages` 保留 `AIMessage(tool_calls)` 与 `ToolMessage`。这就是 ReAct 的 scratchpad：下一轮模型可看到上一轮决定和真实观察，但该内部状态不直接显示给用户。前端只显示经过脱敏的“正在做什么 / 已完成什么”和结果摘要。

**限制**：每轮最多一个工具调用、最大轮数受限、失败工具从后续候选中移除、每轮只暴露按意图筛选后的少量工具。这样既保留自适应，又避免工具过多导致随机选择和 token 膨胀。

### 2.7 MCP 只做协议转发，绕过统一权限和审计

**症状**：服务端 skill 与客户端工具走不同通道；某些工具跳过用户确认、任务关联、取消或审计；Docker 中后端访问宿主 `127.0.0.1` 直接失败。

**根因**：把 MCP 当作“任何工具都能发现和调用”的全局总线，忽略客户端归属、部署网络和权限边界。

**解决**：采用官方 SDK 的 Streamable HTTP，并把所有工具统一纳入 MCP gateway/审计语义。服务端 skill 可原生执行，但仍走同一能力元数据和调用记录；Electron 工具只经已授权、具名的 MCP 会话调用。后端在 Docker 中需要受控 relay/host gateway 或 Redis 客户端工具队列，不能假设容器中的 loopback 等于宿主机。

**运行保护**：MCP 会话隔离、工具快照、超时、连接缓存、熔断、取消通知和结果脱敏缺一不可。用户确认只能授予有限时间、有限工具和有限范围的调用权，不能因为一次确认永久开放系统能力。

### 2.8 任务已在后台执行，前端却显示 404、0 秒或一直“暂停”

**症状**：切换会话或重启前端后步骤消失；完成后发送按钮仍是停止按钮；耗时显示为 0；轮询 `/agents/jobs/{id}` 返回“任务不存在”。

**根因**：前端把 SSE 连接状态当成任务状态，或依赖进程内状态；任务提交、持久化、快照写入与前端订阅之间存在竞争窗口；秒与毫秒混用。

**解决**：以 Job/持久任务记录为权威；灰度 Temporal 任务则以其 Workflow 与 Job 关联记录为准。Redis 仅保存快照和索引。SSE 断开只影响展示，不能取消后台任务；重进会话时先查询任务快照并以省略号气泡兜底。完成、失败、取消必须收敛为终态并复位前端发送按钮。耗时统一在服务端保存毫秒并在前端格式化，不能在传递途中重复除以 1000。

**回归检查**：执行中切换会话、刷新前端、取消任务、完成后继续发送四种场景都要覆盖。

### 2.9 402/400 后任务不结束，或把所有 400 都说成“模型不支持”

**症状**：余额不足后任务永久运行；真实原因是未知高级参数，却提示“模型名不支持”。

**根因**：模型异常只按 HTTP 状态粗分，失败没有被写成终态；兼容接口对请求字段的支持不同。

**解决**：模型错误至少区分余额不足（402）、鉴权（401）、模型不存在（404）、不支持的高级参数、其他配置错误和暂时不可用。前五类应结束办公任务并给出下一步，不做盲重试。`reasoning_effort` 默认不向 OpenAI-compatible 接口发送，只有 `LLM_REASONING_EFFORT_MODELS` 明确白名单的模型才透传。历史 UI 显示名会被规范为实际模型 ID，例如 `DeepSeek V4 Flash` → `deepseek-v4-flash`。

### 2.10 Docker 构建或沙箱错误被误判为模型/Agent 问题

**症状**：构建镜像时拉取元数据出现 EOF/卡在 SHA 下载；脚本沙箱报 rootfs 只读；办公任务长期没有开始。

**根因**：镜像层下载、Docker daemon 权限、容器只读根目录与输入/输出挂载策略是独立基础设施问题，不是 LLM 规划问题。

**解决**：先用 Docker 日志确认构建和运行状态，再检查沙箱的临时输入、授权输出目录和可写挂载。只读 rootfs 是安全基线，应用不得尝试在容器根目录写入；脚本只能在显式可写的工作目录生成产物。镜像没有变化时不要习惯性 `--build`，避免无意义的镜像拉取和缓存失效。

## 3. 推荐排障顺序

```text
确认模式与任务提交
  -> 确认 TCA 层级和已选附件
  -> 确认候选工具、权限和用户确认
  -> 检查节点进度、资源锁与任务快照
  -> 检查 MCP/沙箱/模型的结构化错误
  -> 验证真实产物与前端预览、下载
```

不要从最终聊天文本倒推真实执行。每一步都应有可查询的任务 ID、节点状态、脱敏错误码、耗时、工具结果和产物验证记录。对于疑似提示词注入，先确认不可信内容是否被错误地当作了任务清单或系统指令，而不是让模型自行“判断是否可信”。

## 4. 每次改动后的最小验证集

```powershell
# 模型配置、错误归因、LangChain 模型参数
.\.venv\Scripts\python.exe -m pytest -q tests/test_model_config.py tests/test_langchain_models.py tests/test_skill_recovery.py

# MCP 会话、缓存、任务关联与取消
.\.venv\Scripts\python.exe -m pytest -q tests/test_mcp_manager.py

# 办公编排、ReAct、工具与产物路径
.\.venv\Scripts\python.exe -m pytest -q tests/test_orchestration.py tests/test_react_runner.py tests/test_skills.py

# 全量回归
.\.venv\Scripts\python.exe -m pytest -q
```

端到端验收至少覆盖：普通聊天不会进入办公 DAG、单文件转换生成且可预览产物、读取失败能有限切换方法、跨领域工具受确认和权限约束、切换会话后仍能恢复任务进度、模型 400/402 会正常结束任务。

## 5. 变更检查清单

- 新工具是否具有明确 schema、权限、资源、幂等性、领域和意图标签？
- 新的写操作是否有产物校验、前端预览和用户主动下载？
- 新的失败类型是否被分类为重试、重规划、请求确认或终止，而非统一报错？
- 新的 MCP 工具是否经过用户归属、会话隔离、审计、取消和脱敏？
- 新的路由规则是否会把附件正文当作指令，或把普通聊天误送入办公模式？
- 是否新增了针对该故障的回归测试，并避免无必要的镜像重建？
