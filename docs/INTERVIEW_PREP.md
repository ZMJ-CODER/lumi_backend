# Lumi 项目秋招面试准备

> 定位：以本项目为"弹药"，覆盖 2026 后端/AI 应用岗面试高频考点。
> 思路：每个考点先给结论，再给"项目里怎么做的"（有代码/日志证据），最后给一句"追问怎么接"。

## 0. 项目一句话介绍（自我介绍用）

Lumi 是一个**多智能体办公助手**：FastAPI 后端 + Electron 桌面端（React），
提供普通对话（按需 RAG + 工具候选路由）与办公模式（上传文档 → 持久化多智能体 DAG → 分析/编辑/产出）两条链路；
底层自研了 RAG 索引、独立 orchestration 内核、可灰度 Temporal 运行时、MCP 混合技能架构、缓冲式文档编辑与本地沙箱。

## 1. 系统设计（权重 35-40%）

### 1.1 在线文档编辑系统（真题高频）
面试题："设计一个支持千万用户的在线文档编辑系统。"

**项目结合点（真实做过）**：
- 结构化编辑而非二进制覆盖：docx/xlsx/pptx 走"结构读取 → LLM 生成编辑指令 JSON → 应用到缓冲副本"，
  避免损坏文件结构（`app/services/office_docs.py` 的 OP_SCHEMAS）。
- **缓冲 + 人工审核落盘**：编辑只写 `buffered` 副本，前端 Office 同款预览，用户"保留/撤销"后才 commit 回原文件。
- 只读/可编辑分治：PDF/ODT/图片走 OCR 只读，文本类全量重写/补丁，老版 Office 走本机 COM。

**追问承接**：并发编辑冲突 → 目前单用户单人编辑，预留按段落版本号做乐观锁；
服务端会话 TTL + 前端 20 轮挂载上限兜底清理。

### 1.2 文件上传系统
面试题："设计一个支持大文件、断点续传、进度展示的上传系统。"

**项目结合点**：
- XHR 上传 + 进度回调（非 fetch，拿得到 `upload.onprogress`），前端卡片实时百分比 + 取消（`xhr.abort()`）。
- 分类上传：图片/音频走附件，办公文档走 office 会话（30MB 上限、超时 3 分钟、可取消）。
- 上传成功挂载为"随消息携带的文档"，20 轮自动解除；服务端 TTL 兜底。

**追问承接**：大文件分片/秒传 → 目前面向个人使用未做分片，可扩展：前端 sha256 秒传、分片并发上传、
服务端合并 + 校验。

### 1.3 限流 / 缓存 / 连接池（必考八股落地）
- 限流：Redis INCR 滑动窗口，按 IP 分 auth（20/min）与通用（300/min），Redis 挂了放行（防击穿）。
- 缓存：健康检查 TTL 缓存（5s/1s 降级探测），避免探活打满连接池（实测修复后 health RPS 93→344→900+）。
- 连接池：`DB_POOL_SIZE/DB_MAX_OVERFLOW` 可配置，多 worker 下总数不超过 Postgres `max_connections`。

## 2. AI 应用岗必考：RAG / Agent / MCP / Prompt

### 2.1 RAG
**高频题：为什么混合检索？chunk 怎么切？怎么治理幻觉？**
- 项目答案：`bge-m3` 1024 维向量 + pgvector（ivfflat）余弦检索；分块按"段落→句子→标点"优先级切，
  带重叠窗口（`split_text`）；小文档全文直注入（≤20KB 不检索，防阈值漏召回）。
- 幻觉治理：检索阈值（相关性 < 0.7 不可信）、限定"仅依据给定片段作答，不要编造"、
  引用来源回传前端（citations）。
- 踩坑复盘（面试加分）：上传后"模型只看到标题"→ 定位是只传 metadata 没传正文，改为文档结构注入；
  用户问文档里四个字查不到 → 阈值被绕过 + 分块粒度问题，最后固定阈值并加全文直注入。

### 2.2 Agent / Multi-Agent 编排
**高频题：多 Agent 怎么协作？任务怎么拆？失败怎么处理？**
- 项目答案：**意图分类 → 模板/模式/自由规划三级路由**（模板优先，LLM 自由规划兜底）；
  模板库 6 个（文档分析/发票筛选/早晚报/对比/合并/翻译）+ 模式库（ETL/Router）。
- DAG 校验：无环、节点唯一、工具已注册、参数必填；默认持久化 DAG 执行，安全的静态只读任务才灰度 Temporal。
- 失败策略：任务级摘要写 Redis 供下次规划延续；节点级硬超时、有限重试和 effect journal 保护执行；不可逆副作用不自动重放。
- 文档兜底：规划结果没覆盖到已上传文档时，强制补 `office_doc` 分析节点（不依赖 LLM 自觉）。

### 2.3 MCP / 可插拔技能
**高频题：MCP 是什么？为什么用？工具怎么管理？**
- 项目答案：**混合架构**——服务端技能（文档处理/LLM 调用）用原生函数注册；
  客户端技能（打开软件/读写本地文件/发邮件）通过 Electron 主进程暴露的 MCP server
  （`http://127.0.0.1:8765/mcp`）调用，可插拔、可热更新。
- 工具治理：技能按场景白名单暴露（`scenes`）、写操作分级（高危需确认）、
  客户端请求走 Redis 轮询或 MCP 直连双通道、审计日志（control_logs）。

### 2.4 Prompt / 推理强度
- 办公脚本两阶段生成：先"伪代码（逻辑层）"再"实现层"（解耦逻辑与语法，实测显著降低反复试错）。
- 规划器与执行器分离：规划用低推理强度 + 16k token 上限，执行用高推理强度，避免规划阶段烧 token。

## 3. 高并发八股（结合项目实测数据）

| 考点 | 八股结论 | 项目实测 |
| --- | --- | --- |
| 异步化 | CPU 密集任务不能阻塞事件循环 | OCR 阻塞时 health 卡 3s → `asyncio.to_thread` 修复后 <30ms |
| 日志 I/O | 同步写日志会拖垮高并发 | 访问日志串行时 health 344 RPS → 队列日志/关日志后 900-1400 RPS |
| 连接池 | 池大小要和 DB 上限匹配 | 池过大打爆 Postgres 100 连接 → 可配置 10+20/进程 |
| 多进程扩展 | 单进程有 GIL/池锁上限，靠 worker 线性扩展 | 1w→4w：health 882→1382 RPS；/me 59→79 RPS |
| 缓存穿透/击穿 | 用空值缓存 + 互斥锁 | 健康检查 TTL 缓存防止探活打满连接池 |
| 消息队列 | 削峰填谷、异步解耦 | Celery（文档处理/向量化异步执行） |
| 限流 | 滑动窗口/令牌桶 | Redis INCR + IP 分级限流，Redis 故障放行 |

## 4. 高频 Q&A（含踩坑复盘，最有说服力）

**Q1：项目最大的一次性能事故？怎么排查的？**
答：OCR 上传把事件循环卡死。排查链路：压测发现 health 在 OCR 期间延迟飙到 3s →
读代码确认 `read_structure` 是同步 CPU 密集调用 → 用 `asyncio.to_thread` 切线程池 →
再压测 health 恢复 <30ms。后续又发现 uvicorn 访问日志写文件也是串行瓶颈，
用 QueueHandler + 监听线程解决，Linux 容器下验证 900+ RPS。

**Q2：为什么模型"看不见"上传的文档？**
答：分两层——前端只把文档标题拼进消息，正文没传；后端分析接口只在文档 ≤20KB 时全文注入，
否则走 RAG 且阈值可能过滤掉精确词。修复：正文注入 + 固定阈值 0.7 + 文档强制分析节点兜底。

**Q3：Windows 上模型下载为什么失败？**
答：三连坑——huggingface_hub 1.x 默认 xet 协议（国内连 CAS 服务器 401/超时）→ 禁 xet 走镜像；
Docling 布局模型缓存不完整 → 删缓存重下；torch.compile 需要 Triton（Windows 没有）→ 关编译。
这些"环境适配"踩坑在面试里很加分，说明有真实部署经验。

**Q4：多 Agent 会不会失控/重复执行？**
答：规划器输出 DAG 前做静态校验；Job 状态、逻辑计划和 effect journal 保证默认运行时的恢复与幂等；任务级摘要标记已完成步骤
传给下次规划，避免重复执行；高危节点（发邮件/审批）挂人工确认门控。

## 5. 面试话术模板（STAR）

- **S**：个人 AI 办公助手，解决"上传文档后模型看不到、写代码慢、改文件不落盘"三类问题。
- **T**：既要 RAG/多智能体/文档编辑能力，又要单机可部署、Windows 可用、高并发可扩展。
- **A**：分三层——数据层（pgvector + 文档解析 + OCR）、编排层（意图分类 + 模板 DAG + 独立内核 + Temporal 灰度）、
  执行层（服务端技能 + MCP 客户端技能 + 缓冲编辑 + 沙箱）。
- **R**：以 CI 最新输出为准（ruff 与 pytest 全绿后记录构建号），压测结果见 `CONCURRENCY_PERF.md` 的历史快照，
  Linux 容器 CUDA 可用、OCR 端到端识别正确。

## 6. 薄弱点自查（诚实面对）

- 未做真正的分布式：单机部署，多 worker 共享 Postgres/Redis；面试可主动讲"下一步"（读写分离、
  Kafka 削峰、分片）。
- 文档协作冲突未实现：当前单用户；可讲乐观锁/CRDT 方向。
- 大文件上传无分片：可讲秒传/分片/断点续传方案。
- 无 K8s：Docker Compose + Dockerfile；可讲容器化已就绪，K8s 只是编排层。
